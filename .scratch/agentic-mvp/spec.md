# Agentic MVP：真实 GM 的开放式 CLI 短篇

Status: ready-for-agent

## Delivery Status

截至 2026-07-31，Increment 1 已由独立的 opt-in Agentic 路径交付：不可变会话、GM 最终答复与事实账本、`make_check`、真实 DeepSeek adapter、连续 CLI 和两回合开放行动证据均已完成。默认入口仍保留旧规则驱动基线；正式恢复、其余 COC 工具、完整短篇、模型评估矩阵和旧路径退役仍按下述目标与迁移顺序实施。以下 Problem Statement 保留为本规格建立时的迁移起点，不代表当前交付状态。

## Problem Statement

当前运行时仍是规则驱动的旧基线：模组 JSON 同时承担叙事内容、场景投影、检定授权和效果白名单；有限 `GameMasterAgent` 只能在旧工具和旧 `GameMasterDraft` 契约内工作；CLI 只能初始化并展示开场状态。它还没有真实 DeepSeek adapter、自然语言事实账本、完整回合记录、最终答复的原子提交或未完成回合恢复。

这使玩家不能可靠地用参考书未预写的行动改变世界，也无法验证同一个真实 LLM GM 是否能在后续回合承认自己建立的因果。与此同时，把旧效果授权链继续扩展会让 Harness 代替 GM 审批故事能否发生，削弱玩家的调查员主动意志，并把一个八周 MVP 推向通用多 Agent 或多 provider 基础设施。

项目需要一份可直接拆解和实现的统一规格，明确 GM、Agent Harness、COC 机械、正典、持久化、恢复、CLI 和评估之间的责任边界，并让当前源码与目标设计的差异保持可见。

## Solution

交付一局由真实 DeepSeek 游戏主持人驱动的中文 CLI《逃离塔纳里昂》短篇。玩家以自由文本控制自己的调查员；同一个 GM 负责理解意图、扮演所有 NPC、裁定虚构因果、建立正典并决定何时需要 COC 机械。Agent Harness 只负责受信 COC 结算、结构校验、可见性、持久化、运行保险丝和恢复，不判断模组是否预写了某个故事后果。

系统保留一个连续的 GM Agent Loop。GM 每次响应只能调用一个当前提供的 COC 语义工具，或提交包含 `narration`、`establish`、`retire`、`session_status` 的最终答复。机械结果在工具成功后立即原子持久化；最终成功提交在同一次原子替换中写入 `CommittedTurn`、公开和隐藏事实变化、`session_status`，并将 `incomplete_turn` 清为 `null`。隐藏事实是持久化的可信正典，会继续提供给 GM，但从玩家投影、公开报告和普通日志中过滤。模型或 provider 中断时，已提交机械不回滚，回合保留为未完成状态，玩家明确恢复同一 `turn_id` 后继续，不重掷或重复扣减。

实现顺序先证明真实 DeepSeek 能接住一次模组未预写行动，直接裁定或调用 `make_check`，建立由该行动造成的新事实并在下一回合继续承认其后果，再补齐恢复、完整 COC 工具、人物与开放收束，最后用确定性测试和真实模型评估选择默认配置并退役旧路径。CLI 是唯一正式玩家界面；不建设 router、planner、critic、角色 Agent、Memory Agent、通用 provider 路由或第二套模组接入机制。

## User Stories

1. As a 玩家, I want to start a new《逃离塔纳里昂》session from the CLI, so that I can enter the game from a clear opening situation.
2. As a 玩家, I want the opening narration and minimum opening canon to be loaded before my first input, so that the first action has a stable fictional context.
3. As a 玩家, I want to select a pregenerated investigator and customize my display name, honorific, pronouns, occupation wording, appearance, background hook, and keepsake, so that the investigator reflects my identity without changing COC mechanics.
4. As a 玩家, I want my `InvestigatorProfile` to remain frozen for the session, so that later model responses cannot silently rewrite my identity.
5. As a 玩家, I want to describe actions in free text instead of choosing from a route menu, so that I can attempt plans the reference book did not enumerate.
6. As a 玩家, I want a reasonable unplanned action with a clear outcome to be resolved directly, so that the Harness does not manufacture a roll or reject it because no scene or effect ID exists.
7. As a 玩家, I want a committed public check to display the action, ability, difficulty, and failure stakes that the GM fixed before the roll together with the result, so that I can verify the mechanic used predeclared parameters without adding a pre-roll confirmation pause.
8. As a 玩家, I want the GM to choose whether a COC check is needed, so that ordinary actions remain fluid while meaningful uncertainty creates tension.
9. As a 玩家, I want every check resolving my declared action and every HP, SAN, or Luck change to my investigator to be public as soon as it is committed, so that the GM cannot hide mechanics that belong to my character.
10. As a 玩家, I want the GM to explain committed dice and character-value changes faithfully, so that fictional narration cannot rewrite mechanical authority.
11. As a 玩家, I want to decide whether to spend Luck after an eligible failed check, so that resource costs remain my choice rather than an automatic optimization.
12. As a 玩家, I want to propose a different approach before a pushed roll and explicitly accept its more severe failure risk, so that a push is a meaningful decision rather than a free reroll.
13. As a 玩家, I want damage and Sanity changes to come from trusted COC tools, so that the GM cannot submit arbitrary HP or SAN patches.
14. As a 玩家, I want hidden NPC or secret mechanics to remain hidden until the fiction reveals them, so that suspense is preserved without losing a complete record.
15. As a 玩家, I want the GM to preserve my investigator's unspoken choices, dialogue, beliefs, and relationship commitments, so that the system does not play my character for me.
16. As a 玩家, I want NPCs and AI teammates to make decisions and react through the same GM, so that they feel like participants with motives rather than separate tool menus.
17. As a 玩家, I want relationships, clues, threats, and route changes to emerge as natural-language facts, so that the world can evolve without a fixed relationship table or threat clock.
18. As a 玩家, I want a reasonable action absent from the reference book to be resolved directly or through `make_check` and establish a fact caused by that action which affects the next turn, so that open play demonstrably changes the world rather than merely appending an unrelated fact.
19. As a 玩家, I want an outdated fact to be retired with a reason while its history remains, so that changes in the world are traceable rather than silently overwritten.
20. As a 玩家, I want a hidden fact to remain persisted trusted canon until an in-fiction reveal retires the hidden record, establishes the corresponding public fact, and presents the reveal in narration, so that disclosure is traceable without rewriting history.
21. As a 玩家, I want the final narration to appear only after its structure and fact references are valid and committed, so that I never see rejected or partial story text as canon.
22. As a 玩家, I want the session to end when the fictional core problem is resolved, so that I can reach an escape, bargain, sacrifice, departure, or other earned conclusion without a predefined `ending_id`.
23. As a 玩家, I want the CLI to distinguish committed public mechanics, committed narration, and technical interruption, so that I know what happened in the fiction and what requires operational action.
24. As a 玩家, I want an interrupted turn to block new fictional input, so that a new action cannot race with an unresolved prior turn.
25. As a 玩家, I want to explicitly choose “resume” or “exit” after an interruption, so that recovery never creates model calls, cost, or fictional progress without my consent.
26. As a 玩家, I want recovery to reuse the same `turn_id`, original input, tool interactions, and committed mechanics, so that resuming cannot create a hidden reroll or duplicate resource loss.
27. As a 玩家, I want repeated recovery attempts to be idempotent, so that restarts and repeated commands do not duplicate facts, turns, or character-value changes.
28. As a GM model, I want the complete immutable module and character reference plus all current public and hidden facts and the trusted full game record in context, so that I can improvise while respecting established canon.
29. As a GM model, I want a small semantic COC tool directory, so that I can request trustworthy mechanics without learning storage paths, effect whitelists, or arbitrary state patches.
30. As a GM model, I want committed tool results returned to the same continuous loop with their protocol identifiers, so that I can interpret outcomes and finish the same turn.
31. As a GM model, I want concrete local schema errors when my final response is invalid, so that I can repair structure without a second critic or a second Agent.
32. As an Agent Harness, I want to own game IDs, turn IDs, fact IDs, mechanic IDs, actor data, and persistence, so that model output cannot forge runtime authority.
33. As an Agent Harness, I want to validate COC parameters against frozen `ActorSheet` data and calculate rolls, success levels, HP, SAN, Luck, armor, and thresholds, so that mechanical truth is deterministic and auditable.
34. As an Agent Harness, I want each successful tool call to persist the mechanic, character changes, interaction, and assistant/tool protocol messages atomically before returning success, so that recovery has one authoritative result.
35. As an Agent Harness, I want final narration, fact changes, session status, the committed turn record, and `incomplete_turn = null` to persist in one atomic replacement, so that no partial fiction becomes canon and recovery cannot replay an already committed turn.
36. As an Agent Harness, I want an invalid single-tool call with a usable `tool_call_id` to produce no roll or state change while atomically persisting its failed `ToolInteraction` and assistant/tool protocol messages before feedback, so that recovery can reconstruct the exact provider conversation.
37. As an Agent Harness, I want to execute none of a multiple-tool response, return persisted per-ID errors only when every ID is usable and unique and budget remains, and otherwise interrupt with preserved protocol state, so that recovery never depends on an ambiguous assistant/tool pairing.
38. As an Agent Harness, I want to enforce an eight-response limit, a 60-second request limit, a 180-second attempt limit, and one local final-structure repair while processing the eighth response by its actual type and never requesting a ninth, so that provider failures have bounded cost without discarding a valid final response or mechanic.
39. As an Agent Harness, I want provider diagnostics and thinking `reasoning_content` isolated from player records and normal output, so that debugging does not leak secrets or hidden reasoning.
40. As a CLI integrator, I want only “start new turn” and “resume incomplete turn” concepts exposed at the player boundary, so that orchestration, storage, model messages, and COC details remain behind one deep interface.
41. As a CLI integrator, I want the first version to use non-streaming model output, so that only validated narration is shown while public mechanics can still appear immediately after commitment.
42. As a developer, I want a thin `GameMasterModel` seam that accepts both a real DeepSeek adapter and a programmable fake adapter, so that provider behavior is isolated and deterministic failure cases are testable.
43. As a developer, I want to reuse the existing finite single-GM loop, injectable randomness, immutable tool-result projections, and atomic JSON write primitive where they fit, so that migration preserves proven engineering properties without preserving obsolete authority rules.
44. As a developer, I want old rule-driven code and tests to remain as a comparison baseline until each replacement gate passes, so that migration does not hide regressions or silently reinterpret old saves.
45. As a developer, I want the new path to use explicit schema versions and immutable Markdown/reference snapshots, so that later edits to working-tree content cannot change an existing session.
46. As a developer, I want the runtime to reject missing, corrupt, mismatched, or unavailable frozen inputs before model invocation, so that failures are deterministic and do not produce partial fictional progress.
47. As a test author, I want high-seam behavior tests to use temporary real session data and public lifecycle calls, so that tests verify externally observable persistence and visibility rather than private helper implementation.
48. As a test author, I want independent expected dice outcomes and counterexamples for every COC boundary, so that tests do not merely reproduce the implementation's own calculations.

56. As a maintainer, I want the final migration to remove obsolete request/effect authorization, fixed scenes, relationship stages, threat clocks, and fallback fiction only after replacement evidence passes, so that the production path has one clear authority model.
57. As a maintainer, I want implementation ticketing to start at Increment 1 because Increment 0 documentation and contracts are already complete, so that the tracker does not duplicate finished design work.

## Implementation Decisions

- **Authority split.** The GM owns fictional causality, NPC portrayal, and canon. The player owns the investigator's intent and meaningful choices. The Agent Harness owns COC mechanics, structural validation, persistence, recovery, and player-visible projection. The module reference is prose guidance, not a permission table.

- **One continuous loop.** There is one GM Agent Loop per turn. It may stop with a final response or call one currently enabled COC tool and continue with the result. No router, planner, critic, semantic validator, Memory Agent, character Agent, fixed OODA workflow, strategy label, or fallback-story generator is part of this MVP.

- **Highest stable seams.** The player-facing seam is the Agent Harness lifecycle: start a new turn or resume an incomplete turn, returning committed public events or a technical interruption. The only external-provider seam is `GameMasterModel`, which receives the assembled non-streaming request and returns a preserved `ModelResponse` envelope. Deterministic tests inject a programmable fake adapter through that seam; they do not add a second orchestration interface.

- **Provider adapter.** `DeepSeekGameMasterModel` uses the OpenAI Python SDK with Chat Completions and the DeepSeek base URL. It does not use the Responses API, a provider registry, automatic model routing, or automatic fallback. The first protocol baseline is `deepseek-v4-flash` with non-thinking and non-streaming output; model ID and thinking mode remain explicit runtime configuration for later evaluation. API keys are injected by the composition boundary and never persisted or logged.

- **Session setup and snapshots.** New-game initialization atomically freezes a `SessionSetup`, minimum opening canon, selected investigator `ActorSheet`, optional mechanically relevant NPC sheets, `InvestigatorProfile`, display names, skill-catalog version, and content-hash-addressed Markdown module/character snapshots. The CLI displays opening narration before accepting the first player input and never creates a model turn without player input. Existing sessions never fall back to mutable working-tree references.

- **Runtime authority identifiers.** The Harness generates and owns `game_id`, `turn_id`, `fact_id`, and `mechanic_id`. Provider `tool_call_id` is preserved only as protocol correlation data and is validated for uniqueness and replay. The GM cannot create or overwrite game identifiers, target values, dice, outcomes, state paths, or mechanical records.

- **Investigator and actor data.** `InvestigatorProfile` stores player-authored identity expression and is separate from mechanical `ActorSheet` values. Frozen actor sheets provide only the attributes, normalized skills, HP, SAN, Luck, and armor needed by the COC tools. Runtime GM tools cannot create or edit actor sheets. NPCs without a need for trusted mechanics remain fictional participants without dynamic sheets.

- **Context assembly.** Each initial request includes the capability charter, final-response contract, immutable setup and full Markdown references, investigator profile, relevant actor sheets, current public and hidden active facts, the complete committed game record, the original player input, and the currently enabled COC tool definitions. Subsequent requests append preserved assistant/tool protocol messages and trusted results. MVP does not add RAG, summaries, vector search, scene projections, or a Memory Agent.

- **COC tool surface and contract-specific parameters.** The final MVP exposes `make_check`, `push_check`, `spend_luck`, `deal_damage`, and `make_sanity_check`. The first vertical slice implements only `make_check`. Each tool fixes and validates only the inputs defined by its own contract before its first random draw or state commit: `make_check` fixes action, ability, difficulty, dice adjustment, failure stakes, and visibility; the other tools use their own fields such as `check_id`, points, a new approach, damage parameters, or SAN-loss expressions. The Harness then reads frozen actor values and prior trusted mechanic records as required, applies the relevant COC rule, and persists the result. A public mechanic displays that tool's applicable precommitted inputs together with the committed result; the MVP does not add a separate pre-roll pause or player-confirmation event. The Harness structurally forces every investigator HP, SAN, or Luck change to `public`, validates check visibility before randomness, and never permits post-result visibility changes. It does not classify natural-language intent or add an initiator field: the GM must mark player-declared investigator checks public and may mark only NPC actions or genuinely secret judgments hidden before the roll. Capability guidance and real focused hard gates verify that semantic responsibility. Tools do not accept module target IDs, rule IDs, effect IDs, arbitrary JSON paths, or story-specific patches.

- **Player-choice mechanics.** `push_check` requires a prior eligible failed check, a different approach, and a player-accepted worse failure stake. `spend_luck` requires explicit player choice in the current input and a valid balance/eligibility check. The Harness validates mechanical association and balance but does not implement a natural-language intent classifier; real GM scenarios verify that the model does not choose for the player.

- **Tool protocol and idempotency.** A provider response with one tool call first requires a usable `tool_call_id`: a JSON string whose value is non-empty and exactly equal to its trimmed form; no other normalization is applied. IDs must also be unique within one assistant response. If an ID is missing or unusable, reliable assistant/tool pairing is impossible: the Harness atomically appends a restricted `provider_protocol_errors` record containing the serialized raw provider envelope and `provider_protocol_error`, leaves the replayable `deepseek_messages` prefix unchanged, creates no `ToolInteraction` or synthetic tool-result message, and interrupts. Otherwise the call is validated and either executes or produces a structured error. Before either result returns to the GM, one atomic `session.json` replacement stores the original assistant tool-call message, a `ToolInteraction` containing `arguments_raw` and the normalized `arguments` when available, and the corresponding tool-result message; success additionally stores the mechanic and actor-value changes. Invalid arguments produce no random draw, `mechanic_id`, or state change, but still persist an `ok: false` interaction and protocol messages so recovery can replay them. For `(turn_id, tool_call_id)`, idempotency compares normalized arguments when they exist and otherwise compares the exact `arguments_raw`; the same value replays the saved result, while a different value is a protocol error. A response with multiple calls executes none. When every ID is usable and unique, the Harness atomically persists the assistant message plus one `multiple_tool_calls_not_allowed` tool error per ID; if response and time budget remain, those errors return to the same GM and the loop continues, otherwise the saved protocol state ends in a technical interruption. When any ID is missing, unusable, or duplicated, the Harness records the raw envelope in `provider_protocol_errors`, leaves the replayable message prefix unchanged, creates no synthetic per-ID tool responses, and interrupts.

- **Mechanical commit ordering.** A successful COC call atomically writes its mechanic record, actor-value changes, interaction, provider assistant/tool messages, and replay identity before reporting success to the GM or CLI. Mechanics are never rolled back, deleted, or re-run because later narration fails. A public mechanic is shown immediately after this commit with the contract-specific inputs fixed before randomness or mutation plus the committed result; for `make_check`, these include action, ability, difficulty, dice adjustment, and failure stakes. Hidden mechanics are recorded and returned to the GM but not shown to the player.

- **Final response contract.** The GM emits only `narration`, `establish`, `retire`, and `session_status`. `narration` is player-visible prose; `establish` contains public or hidden natural-language facts; `retire` references active facts by `fact_id` and includes a reason; `session_status` is `ongoing` or `complete`. The GM does not emit IDs, mechanic copies, tool traces, suggested-action menus, strategy, diagnostics, or `ending_id`.

- **Canon and facts.** `SessionSetup` establishes only minimum opening canon. A GM's successfully committed explicit narration and submitted public or hidden fact changes become canon; the fact index is a recall projection, not a permission layer. Both visibility classes are persisted in `session.json`, the fact ledger, and the trusted GM game record, and every later GM request receives all still-active public and hidden facts. Player projections and defined public outputs filter hidden fact text. Facts use active/retired history, stable IDs, visibility, and origin. Meaning changes retire the old fact and establish a new one. Revealing a hidden fact does not mutate its visibility in place: one valid final response narrates the disclosure, retires the hidden `FactRecord`, and establishes the corresponding public fact, preserving both history and the new player-visible state. Harness validates structure and references, not whether a free-text consequence is narratively allowed. A fact omitted from the index but explicitly established in committed narration remains traceable in the full record.

- **One aggregate and bounded projections.** `session.json` is the only MVP runtime aggregate. The fact ledger, `CommittedTurn` history, trusted GM game record, mechanic records, and incomplete-turn state are logical collections or reconstructed projections within that aggregate, not separate databases or services. The only required public projections are the existing CLI player/technical output and the evaluation artifacts defined in `evaluation.md`; privacy requirements do not authorize a generic logging, reporting, or observability framework.

- **Final validation and atomicity.** The Harness locally parses and validates final JSON types, enumerations, unknown fields, fact references, duplicate retirements, and atomic applicability. An invalid first response receives one concise schema/reference repair request from the same GM with tools disabled; the repair counts toward the same attempt budget and cannot rerun mechanics. A valid final response is committed through one `session.json` atomic replacement that writes the `CommittedTurn`, all public and hidden `establish`/`retire` changes, the new `session_status`, and `incomplete_turn = null`. The Harness must not commit the turn and clear the incomplete marker in separate writes. A second invalid response or failed final write leaves narration and fact changes uncommitted and retains the incomplete turn.

- **Incomplete turns and recovery.** The Harness creates and persists an incomplete-turn shell immediately after accepting input and allocating `turn_id`. It stores the original input, frozen model/tool profile, attempt limits, replayable provider messages, tool interactions, committed mechanic references, failure code, and cumulative diagnostics in restricted incomplete-turn recovery state. `deepseek_messages` contains only a provider-valid replay prefix; an unpairable response is retained separately as a serialized `provider_protocol_errors` record and is never sent back to DeepSeek. Those diagnostics are not committed game records, fact-ledger entries, player output, or ordinary logs; API keys are never stored, and provider hidden reasoning is retained only in restricted recovery data when required for diagnosis or protocol restoration. Explicit recovery uses the same `turn_id`, input, session canon, model profile, and already committed tool results, starts a new execution attempt from the last valid provider-message prefix, and never accepts a new fictional action or reruns a mechanic.

- **Runtime limits and ordinary failures.** Each attempt defaults to at most 8 model responses, 60 seconds per request, and 180 seconds total, with one final-structure repair. These are cost/reliability limits, not story budgets or fictional time. Before the eighth response, a structured single-tool error or a multiple-tool response with complete usable unique IDs may be persisted, returned to the same GM, and followed by another response while budget and time remain. Provider errors, empty/truncated responses, unknown steps, timeouts, unpairable tool-call responses, exhausted budget, and final-write failures produce a stable technical interruption. Harness never invents a fallback narration, compensates with an extra LLM call, or rolls back committed mechanics.

- **Eighth-response control flow.** The eighth model response is processed, but the Harness never requests a ninth. A legal single tool call with a usable ID is executed and its mechanic or structured tool error plus protocol messages are persisted; the turn then remains incomplete with a step-limit interruption for explicit recovery. A legal final response is validated and, if valid, receives the normal atomic final commit. An invalid final response that would require repair, a tool error, or a multiple-call response with complete usable unique IDs has its available validation/error protocol state persisted and then interrupts because no continuation response remains. A single-tool response with a missing or unusable ID, or a multiple-call response with a missing, unusable, or duplicate ID, atomically records the raw provider protocol event and interrupts.

- **CLI boundary.** The CLI is the only formal player interface. It composes configuration and adapters, displays opening text, sends free-text actions, displays public mechanics and committed narration, and offers explicit resume/exit for incomplete turns. It does not parse intent, select tools, own facts, access hidden provider content, or expose model reasoning, hidden mechanics, or internal diagnostics.

- **Migration increments and gates.** Increment 0 records the already-completed authority documents, contracts, ADRs, and evaluation fixtures as migration history and as the prerequisite for implementation; later ticketing starts at Increment 1 and creates no duplicate Increment 0 implementation ticket. Increment 1 delivers the real DeepSeek plus `make_check`, facts, two-turn CLI slice and no full recovery promise. Increment 2 adds incomplete-turn persistence, timeouts, one repair, and explicit recovery. Increment 3 adds the remaining four tools and production pregenerated sheets. Increment 4 integrates final module/character content, NPC agency, relationship facts, and open closure. Increment 5 evaluates four DeepSeek configurations and complete playtests. Increment 6 makes the new path the only production path and removes obsolete fixed-scene/effect/relationship/clock/fallback logic. Each implementation increment keeps the old baseline until its replacement gate passes.

- **Compatibility boundary.** Old runtime JSON, old memory, old `request_check`/`apply_effect` authorization, and old saves are not silently converted into new canon. During migration they remain comparison material or an explicitly separate legacy entry point. No permanent dual-runtime abstraction is added to domain modules.

- **Evaluation qualification shortfall.** The 72-run focused matrix produces no default GM by itself. Only when at least two configurations satisfy every hard gate and quality threshold do the two qualifying leaders proceed to two complete playtests each. If zero or one configuration qualifies, the project selects no default, does not lower gates, thresholds, repetitions, or scenario requirements, and returns to model, Prompt, context, or tool-design decisions. Any behavior-affecting change defines a new candidate and requires a complete new matrix before playtests can resume.

- **Security and privacy.** Hidden facts are trusted canon and therefore remain in `session.json`, the fact ledger, and the trusted GM game record. Their text is filtered from player output, public evaluation reports, error output, and ordinary logs. API keys, authentication headers, provider hidden reasoning, and private diagnostics do not enter committed game records, the fact ledger, player output, public reports, error output, or ordinary logs. Thinking protocol data may be stored only as restricted incomplete-turn recovery material when required by the provider.

### Observable Acceptance Gates

- **Vertical slice gate.** A deterministic Harness seam test scripts a first-turn `establish`, proves stable `fact_id` allocation and persistence, and proves the active fact is injected into the captured second-turn GM request; it does not judge whether the fact was a meaningful consequence or whether prose acknowledged it. Separately, the real DeepSeek run for focused scenario one is the semantic gate: the GM must directly resolve or call `make_check` for the reference-book-absent player action, establish at least one fact that the evaluator judges was caused by that action, and explicitly carry that consequence into the second turn. An unrelated, preloaded, or merely decorative fact fails this gate. The new path does not read legacy check rules, effect definitions, allowed-effect IDs, or fixed endings.
- **Mechanical gate.** Every enabled COC tool produces results only from frozen actor data, trusted prior mechanic records, and Harness-owned rules as applicable, after fixing that tool's own contract-defined parameters before randomness or mutation. `make_check` specifically fixes action, ability, difficulty, dice adjustment, failure stakes, and visibility before RNG; no generic requirement for those fields is imposed on `push_check`, `spend_luck`, `deal_damage`, or `make_sanity_check`. After commit, a public mechanic exposes its applicable fixed inputs and result together, without a new pre-roll player pause. The Harness structurally rejects `hidden` for investigator HP, SAN, or Luck changes and prevents every mechanic from changing visibility after randomness. Real focused scenarios must show that the GM marks player-declared investigator checks public and reserves hidden checks for NPC actions or genuinely secret judgments. A GM response cannot change dice, targets, success levels, HP, SAN, Luck, armor, mechanic IDs, or post-result visibility.
- **Canonical submission gate.** A valid final response contains exactly the four agreed top-level fields. One atomic replacement writes the `CommittedTurn`, public and hidden fact establishments/retirements, `session_status`, and `incomplete_turn = null`, or none of them. Invalid structure, duplicate/unknown fact references, and failed writes expose no partial narration or facts; restarting after any failed final write cannot see both a committed turn and a recoverable marker for that same turn.
- **Protocol and eighth-response gate.** A failed single-tool call with a usable ID persists its assistant message, failed `ToolInteraction`, `arguments_raw`, normalized arguments when available, and tool-error message atomically before any continuation; replay falls back to exact raw-argument comparison when normalization failed. A single-tool call with a missing or unusable ID atomically persists a serialized raw provider envelope in `provider_protocol_errors`, sets `last_failure` to the stable `provider_protocol_error` code/message, leaves the replayable message prefix unchanged, creates no synthetic assistant/tool pair or `ToolInteraction`, and interrupts. Complete usable unique IDs on a multiple-tool response create no mechanics, persist per-ID errors, and continue only when a later response is still available; missing, unusable, or duplicate IDs or exhausted response budget interrupt with the raw protocol record preserved. The eighth response follows the explicit final/single-tool/tool-error/multiple-call branches and never causes a ninth request.
- **Recovery gate.** After any provider, timeout, step-limit, structure-repair, or final-write interruption, already committed mechanics remain exactly once and the same incomplete turn is discoverable. Explicit recovery resumes the same input and frozen provider profile without a new turn or reroll; ordinary interruptions continue from the saved provider conversation, while an unpairable response continues from the last valid message prefix and leaves the raw protocol record out of the replay. Startup never auto-resumes or auto-calls the model.
- **Player-authority and visibility gate.** Real focused scenarios show that the GM does not choose investigator actions, dialogue, Luck spending, or pushed-roll acceptance; it marks player-declared investigator checks public, uses hidden mechanics only for NPC actions or genuinely secret judgments, and can keep hidden facts private. Deterministic counterexamples prove that investigator HP, SAN, or Luck changes cannot be hidden and that no mechanic can change visibility after randomness. Hidden facts remain persisted and available to later GM requests while CLI player output, CLI technical errors, and public evaluation artifacts filter them. At least one real focused scenario must observe a valid fictional reveal that narrates the disclosure, retires the hidden fact, establishes the corresponding public fact, and exposes only the new public state to the player. Reasoning content, provider diagnostics, and unvalidated output never enter player-visible records.
- **MVP completion gate.** Deterministic Harness evidence, real DeepSeek contract evidence, and the full six-scenario matrix pass their stated thresholds. At least two configurations must qualify before four top-two complete playtests can begin; zero or one qualifier means no default selection and a new complete candidate matrix after design changes. Only then may the new CLI become the sole production path and obsolete authorization/fixed-state code be removed.

## Testing Decisions

- The primary test seam is the public Agent Harness lifecycle backed by one temporary real `session.json` aggregate. Tests should observe player-visible events, persisted logical collections, derived GM/player projections, fact history, mechanic records, incomplete-turn state, and recovery behavior. They should not create separate fact-ledger, GM-record, report, or log services, and should avoid asserting private helper calls or a particular class/file layout.

- The `GameMasterModel` seam is the only provider adapter seam. A programmable fake adapter scripts direct final responses, one-tool continuations, invalid steps, malformed provider envelopes, multiple calls, timeouts, truncation, provider errors, and recovery. The fake also records requests so tests can assert the original input, immutable context, tool definitions, prior protocol messages, and the absence of API keys, provider hidden reasoning, or private diagnostics from fields where they are forbidden. RNG injection controls deterministic COC examples, and storage-failure injection controls atomicity and recovery boundaries; these are local mechanism test controls, not additional provider or orchestration seams.

- COC tests use an injectable random source and independent expected examples. Cover regular/hard/extreme targets, bonus/penalty dice, critical/fumble boundaries, invalid abilities and expressions, player-choice prerequisites, public/hidden visibility, HP/SAN/Luck changes, and counterexamples. For `make_check`, assert that action, ability, difficulty, failure stakes, dice adjustment, and visibility are fixed before the RNG is invoked, and that the committed public projection displays those parameters with the result without a pre-roll pause. Deterministic visibility cases prove that investigator HP, SAN, or Luck changes reject `hidden`, an accepted hidden check remains hidden and fully recorded, and no saved mechanic can change visibility after RNG. Whether a hidden check was fictionally justified or improperly hid a player-declared action is a real-GM hard-gate judgment, not a Harness semantic assertion. `spend_luck` has no visibility input and its committed result must always be public. Expected values come from confirmed COC examples or fixed dice sequences, not from reusing production calculation helpers.

- Persistence tests use temporary real JSON files and injected storage failure points. They must verify the file contents after a mechanic commit, after a final-response failure, after a partial-write interruption, after restart, and after repeated recovery. A successful final-write test must observe `CommittedTurn`, public/hidden fact changes, `session_status`, and `incomplete_turn = null` in the same resulting aggregate; fault injection must prove there is no intermediate state where the turn is committed but remains recoverable. Assertions must also show no partial final fiction, duplicate mechanics, repeated resource loss, or loss of already committed mechanics.

- Agent Loop tests cover direct final response, a single `make_check` followed by final response, invalid tool names/arguments, 60-second request timeout, 180-second attempt timeout, one repair then success, one repair then interruption, empty/truncated responses, and no fallback narration. A single-tool failure with a usable ID must inspect persisted assistant/tool messages and the failed `ToolInteraction`, interrupt after the error, restart, and reconstruct the same provider conversation; malformed arguments must prove same-ID replay uses exact `arguments_raw`, while changed raw text produces a protocol error. ID validation tests must cover non-string, empty, and whitespace-padded IDs plus duplicate IDs within one response. A separate single-call case with a missing or unusable ID must atomically persist a serialized raw provider envelope in `provider_protocol_errors`, set `last_failure.code = provider_protocol_error`, leave the replayable message prefix unchanged, create no `ToolInteraction` or synthetic tool message, and interrupt; explicit recovery must resend only that valid prefix and must not rerun a mechanic. Multiple-call coverage must separately prove: complete usable unique IDs plus remaining budget persist per-ID errors and continue; complete usable unique IDs with no remaining response persist errors and interrupt; missing, unusable, or duplicate IDs persist only the raw protocol error record and interrupt, then recover from the last valid prefix without synthetic tool results. Eighth-response coverage must separately prove: legal final validates and commits; legal single tool executes/persists then interrupts without a ninth request; invalid final needing repair, structured tool error, or identifiable multiple-call errors persist their protocol state and interrupt without a ninth; any unpairable tool-call response persists the raw protocol record and interrupts.

- Fact and visibility tests cover setup canon, public and hidden `establish`, valid and invalid `retire`, fact history preservation, cross-turn continuity, explicit narration remaining canon when the index omits it, and `session_status=complete` blocking new actions without relying on an `ending_id`. Tests inspect the logical fact ledger and committed-turn record inside the same real `session.json`. One hidden-fact case proves the next GM request receives the still-active hidden fact while CLI player output, CLI technical errors, and the defined public evaluation artifact omit its text. A reveal case then commits narration plus hidden `retire` plus corresponding public `establish`, preserves the retired hidden history, and shows the new public fact in the player projection without adding a generic report or logging subsystem.

- The deterministic two-turn vertical-slice test stops at protocol evidence: a scripted first-turn `establish` receives a stable persisted `fact_id`, and the captured second-turn request contains that active fact. Whether the fact was actually caused by the unplanned action and whether the next GM output meaningfully carries it forward are human-observed requirements of real focused scenario one, not assertions in the provider contract suite.

- Recovery tests cover tool-committed-then-provider-failed turns, repeated process restarts, repeated recovery commands, duplicate `tool_call_id` with same and different arguments, frozen profile unavailability, thinking `reasoning_content` round-trip without leakage, and the rule that startup never invokes the model automatically.

- Prior art to preserve or adapt includes the existing finite `GameMasterAgent` tests with scripted model steps, current outer-engine tests that inspect trusted projections and preserve mechanics on model failure, `ToolExecutor` seam tests with real temporary state, rule tests with deterministic random seeds and negative paths, and storage tests for atomic JSON replacement. These tests describe the legacy contract today; new tests must be additive and target the new public contracts until each migration gate permits removal.

- Real DeepSeek contract tests are a separate evidence lane. They verify the OpenAI SDK Chat Completions request, base URL, tool-call protocol, matching `tool_call_id`, final JSON, non-thinking and thinking message recovery, usage, latency, and stable provider error mapping using an externally injected key. They must never record the key or hidden reasoning, assert fixed prose, or decide whether an open action produced a meaningful causal consequence.

- Real GM evaluation uses six independent focused scenarios: an unplanned reasonable escape attempt, check timing, player-owned push/Luck choices, NPC agency with hidden mechanics and a fact reveal, `establish`/`retire` continuity, and an unplanned bargain/remaining closure. Focused scenario one must show the unplanned action being directly resolved or checked, causing a newly established fact, and changing the second-turn response; scenario four must observe hidden-to-public reveal semantics without prior leakage. Each run first checks six hard gates: protocol legality, mechanical truth, hidden-content control, investigator ownership, canon continuity, and valid open action. Only passing runs receive the human 1-to-5 rubric for fictional causality, improvisation, continuity, NPC performance, pacing, and atmosphere; qualification requires average at least 4 and no dimension below 3.

- Model selection runs `deepseek-v4-flash` and `deepseek-v4-pro` in thinking and non-thinking modes, three repetitions per six scenarios (72 focused runs), and retains all failures. Only when at least two configurations qualify do the top two receive two complete open playtests each. With zero or one qualifier, tests must record that no default was selected, preserve every hard gate and quality threshold, return to model/Prompt/context/tool-design decisions, and rerun a complete new matrix for any changed candidate. This evidence chooses a default configuration; it does not create automatic runtime routing.

- Current baseline evidence is separate from target acceptance: the existing legacy suite has 85 passing tests under `/usr/bin/python3` (Python 3.12.3) with `PYTHONPATH=src python3 -m unittest discover -s tests`. That pass confirms the old baseline only and must not be cited as proof that the Agentic MVP target is implemented.

## Out of Scope

- Web UI, TUI, streaming tokens, account systems, multiplayer concurrency, or remote database infrastructure.
- Generic multi-provider adapters, provider registries, automatic routing, automatic model switching, per-turn model selection, or a broad plugin framework.
- Router, planner, critic, semantic validator, second repair Agent, Memory Agent, character sub-agents, autonomous character planning, or fixed OODA/strategy workflows.
- RAG, vector search, automatic summaries, context-projection by scene, fact-extraction LLMs, or a general world-entity schema.
- Predefined routes, scene IDs as permissions, clue/flag tables, relationship stages, numeric threat clocks, effect whitelists, arbitrary state patches, or enumerated endings.
- Full investigator creation, long-term campaigns, cross-session memory, growth, complete COC combat rounds, chase rules, magic, full madness tables, or all COC rulebook special systems.
- Character-specific temptation branches, a sudden boatman event, a second escape route, real-time fictional timers, generic relationship/teamwork frameworks, and other post-MVP narrative expansions.
- Silent semantic conversion of old runtime JSON, memory, state, ledger, or development saves into new Agentic MVP canon.
- Separate runtime databases or services for the fact ledger, GM record, public reports, error logs, or generic observability; these remain logical collections or bounded projections of the one session aggregate and existing CLI/evaluation paths.
- A new pre-roll pause, approval state, or confirmation UI for ordinary checks; explicit player confirmation remains only for choices such as Push or spending Luck.
- Storing API keys, hidden provider reasoning, private diagnostics, or unvalidated model text in committed game records or player output, and exposing hidden fact text through player projections, public reports, error output, or ordinary logs.

## Further Notes

- This is a target specification, not a claim about the current checkout. The existing finite loop, engine, tools, rules, state, CLI, and tests remain the migration baseline until the relevant increment passes its exit gate.
- The accepted seam decision is intentionally narrow: test the highest public Harness behavior with a fake `GameMasterModel`; do not expose internal context assemblers, storage transactions, or COC helpers merely to make tests easier.
- The first meaningful proof is a real two-turn path in which DeepSeek resolves a reasonable action absent from the reference book, directly or with `make_check`, establishes a fact judged to be caused by that action, and explicitly carries its consequence into the second turn. Deterministic tests separately prove only ID allocation, persistence, and request injection. Full five-tool mechanics, recovery UX, content polish, and model selection follow that proof rather than precede it.
- Increment 0 is completed migration history and a prerequisite, not future implementation work. A later `$to-tickets` run starts at Increment 1 and must not create a duplicate Increment 0 ticket.
- Independent comparison and contract review found no remaining blocking contradiction; this revision is `ready-for-agent` for ticket decomposition and implementation from Increment 1 onward.
- Deterministic tests establish protocol and authority evidence; real DeepSeek tests establish provider and model evidence; human playtests establish quality and immersion evidence. None of these lanes alone proves the whole game.
- This specification revision changes target documentation only; it does not claim that the Agentic MVP runtime is already implemented or alter the legacy baseline behavior.
