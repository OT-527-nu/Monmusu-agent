## 指标定义

- 检定率：含 `make_check` 机械的回合数 / 行动回合数（setup 回合除外）。
- 重掷对：相邻两个回合都掷了同角色同技能、且 action 文本二元组 Jaccard ≥ 0.25。
- S7 脱困：最后一回合叙事或新事实命中出口关键词（码头/栈道/出口/浅湾/上岸/仓库/街道等）。
- 中断：GM 执行超时/协议失败等非提交状态。

## 结果解读（pilot 分析，2026-08-19）

### 试跑期间发现并修复的两个生产 bug（与 A/B 结论无关，但曾阻断实验）

1. **结构修正相位的空 tools 数组被 DeepSeek 拒绝（HTTP 400）**。修正请求按设计
   不携带工具，但 adapter 无条件发送 `"tools": []`，导致每次结构修正都中断为
   `provider_bad_request`。修复：`request.tools` 为空时整体省略 `tools` 键。
2. **回放 assistant 消息的空 `tool_calls` 数组被 DeepSeek 拒绝（HTTP 400）**。
   原始错误体：`Invalid 'messages[3].tool_calls': empty array. Expected an array
   with minimum length 1`。Harness 持久化格式用 `[]` 表示无工具调用，回放前必须
   去掉该键。修复：新增 `normalized_sdk_messages()`，adapter 发送前规范化；
   持久化格式不变，历史会话的挂起修正可恢复。契约 runner 的回放保真指纹对模型
   侧消息应用同一变换（`agentic_contract` 的 `model_request_messages_sha256`）。

   验证：最小复现（无工具、空 tools、json_object、tool_choice 四种形状在空上下文
   下全部 OK）→ 用失败会话的原始消息逐字节重放拿到原始 400 错误体。新增两个
   回归测试（`test_complete_omits_tools_key_when_tools_are_empty`、
   `test_complete_strips_empty_tool_calls_from_assistant_messages`），全量基线
   257 项 OK。修复后重跑：`provider_bad_request` 消失；S7/prose/r0 的双重无效
   答复被正确记录为 `invalid_final_response`（模型侧问题，非协议问题）。

### 硬门槛观察（evaluation.md 场景一/二）

- S1 第一回合确立事实：两变体各局均通过。
- S2「拿钥匙免检」：zen/r1 违反（对拿钥匙掷了 spot_hidden）；prose 两局正确。
- S2「跳断桥应检」：prose/r1 违反（无检定直接叙述落点失误）；zen/r0、prose/r0
  正确掷骰。
- 结论：两个变体都没有稳定区分「免检」与「应检」，且失败方向相反，样本内无法
  判定压缩版优劣。

### 定性发现：下水道困境在两种变体下原样复现

- **S7/zen/r1**：第 3 输入 GM 已给出铁梯（可脱困的出口），第 4 输入玩家按固定
  脚本“继续往前走找出口”，GM 让玩家**走过铁梯继续深入**，随后发明塌墙、绿光
  与湿滑之物——无限走廊模式原样复现。
- **S7/zen/r0**：连续两个 navigate 失败 → 渠底塌陷 → 更深 → 再塌陷，水位到胸口。
  失败=新墙模式原样复现。
- **撬格栅被普遍掷骰**：setup 事实已声明“松动的铁格排水口……可以撬开”，但 3 局
  有效局中有 2 局对撬开动作掷骰（climb / mechanical_repair）且失败，GM 让“松动
  的铁格”卡死。章程的“无分支不掷骰”没有压过模型的“加障碍”先验；更暴露了
  **已确立事实未被当作默认成功的依据**。

### 结论（如实）

1. 纯文本层面的 v3 规则（无论散文版还是格言版）在本轮样本里**没有改变行为**：
   检定率没有方向一致的下降，下水道困境 3 局全数复现。
2. 模型把“玩家继续往前走”读成“生成新障碍场景”的邀请；抽象规则（事毕即剪、
   无分支不掷骰）没能在具体场景中压过这一先验。
3. 格言压缩版与散文版在指标上无显著差异——压缩不丢行为的假设在样本内既不支持
   也不反驳（N 太小）。

### 局限

N=2、输入固定、setup 回合的【】元指令可能诱导 GM 模仿元文本风格、无人工质量
量表、骰子相同但模型采样由 provider 决定。以上只能作为方向性观察，不能作为
evaluation.md 正式矩阵的替代。

### 下一步候选（待讨论）

- 把“已确立事实=默认成功”写成硬规则（setup 已声明可撬开的铁格不应掷骰）；
- 旅行默认快进：“玩家声明走向某地时，跳过途中、兑现意图，除非存在已确立障碍”；
- 更硬的失败语义：“每场景最多一个新障碍；失败不得生成新障碍来重问同一问题”；
- 参考书侧补充暗渠出口（用户提出的后者），给 GM 一个可抵达的目的地。
