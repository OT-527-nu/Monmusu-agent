# ADR-002：由 GameMasterAgent 负责语义路由的轻量 MVP 回合设计

- 状态：Accepted
- 日期：2026-07-17
- 决策范围：Monmusu Agent 8 周 MVP 的输入路由、回合体验、角色参与和内容边界
- 决策关系：依赖并局部取代 [ADR-001](0001-single-gm-agent-and-character-tools.md)
- 局部取代范围：ADR-001 中“保留 `FactSet + TurnMode` 作为 `GameMasterAgent` 外围轻量路由与工具权限机制”的决定
- 后续局部取代：[ADR-004](0004-user-input-gameengine-turn-contract.md) 取代本 ADR 的 `RoundTrigger`、旧 `TurnContext` 字段和模型直接生成最终结果描述
- 相关文档：`../README.md`、`../mvp_design.md`、`../turn_loop.md`、`../game_design.md`、`../character_cards.md`

## 背景

[ADR-001](0001-single-gm-agent-and-character-tools.md) 已经决定：MVP 只保留一个拥有工具循环的 `GameMasterAgent`，三名 AI 队友由隔离上下文的角色生成工具产生，不拥有独立 agent loop。

这个决定降低了 multi-agent 调度、状态冲突、延迟和私密信息泄露风险，但仍没有回答玩家实际经历的回合应该怎样组织。

ADR-001 同时保留了 `InputNormalizer`、`FactSet`、`TurnRouter` 和 `TurnMode` 组成的轻量确定性路由层，用于在 `GameMasterAgent` 启动前解析输入、推导模式并配置工具权限。

进一步评估后认为，这一层在当前 MVP 中会重复 `GameMasterAgent` 已经必须完成的自然语言理解：代码需要从开放式中文输入中判断点名对象、行动意图、是否需要澄清和回合类型，而 GM 随后仍要重新理解同一段输入。若使用规则解析，容易脆弱；若再使用一次 LLM 分类，则增加调用、延迟和失败点。

早期设计把完整回合描述为观察、角色提议、用户授权、检定、状态提交和记忆更新的严格数据流。该设计能够保证正确性，却存在以下体验风险：

- OODA 职责如果成为固定演出顺序，三名角色会退化为侦察、证据和工程报告工具。
- 每个行动都等待用户逐项授权，会让队友像遥控单位。
- 普通回合执行完整流程会增加模型调用、延迟和内容复述。
- 用户只有最终决定权，却缺少自己的能力和行动身份，容易成为审批角色建议的管理者。
- 骰点如果只存在于后台轨迹，玩家难以感受到跑团中的随机性和共同期待。
- 关系记忆如果只写入、不回流到台词，角色不会表现出“记得玩家”。

项目必须在 8 周内完成一个 25—35 分钟、可从 CLI 完整游玩的短篇模组，因此不能同时实现独立角色 Agent、通用情感系统、实时压力和大量人物支线。

## 决策驱动因素

- 玩家能够自由声明菜单外行动，并保留路线、牺牲和重大代价的最终决定权。
- 三名队友既能自然行动，又不能越权控制玩家或正式状态。
- 普通回合足够快，高潮回合才增加角色调用和协作结构。
- 骰点和成功等级对玩家可见，同时仍由确定性代码产生。
- 角色能够通过称呼、身体语言和事件回声表现关系变化。
- 所有新增机制都能在 8 周内由 CLI 验证，不依赖复杂 UI。
- 《逃离塔纳里昂》仍只有一条正式逃生链，不增加新的主要场景或支线。
- 不为尚未实现的路由抽象增加额外类、schema、Prompt 和测试维护成本。
- GM 可以理解开放式语义，但不能自行扩大工具预算、状态权限或正式写入范围。

## 决策

本 ADR 局部取代 ADR-001 对 `FactSet + TurnMode` 外围路由的保留，同时继续遵守 ADR-001 的单 Agent 架构、角色上下文隔离、确定性检定和状态权威。

### 对 ADR-001 的局部取代

自本 ADR 进入 `Accepted` 状态起，ADR-001 中以下决定不再适用于 MVP：

> 保留 `FactSet + TurnMode` 作为 `GameMasterAgent` 外围的轻量路由与工具权限机制。

MVP 不再把以下名称实现为独立运行时组件或规范性数据对象：

- `InputNormalizer`
- `FactSet`
- `TurnRouter`
- 作为权限来源的正式 `TurnMode`

输入流程改为：

```text
RoundTrigger + 用户原文
→ GameEngine 创建包含只读状态快照的最小 TurnContext
→ GameMasterAgent 理解语义并选择回合策略与工具
→ ToolExecutor 验证预算、参数、可见性和行动授权
→ RuleEngine / StateCommitter 产生正式结果
```

`TurnContext` 只保留机械事实：

- `turn_id` 与 `state_version`。
- 明确的触发来源，例如用户输入、系统事件或只读提醒。
- 未经改写的用户原文或结构化系统事件。
- 当前公开状态和记忆的只读快照。
- 是否允许状态变化。
- GameEngine 预先确定的工具集合、调用预算、超时和循环上限。

`RoundTrigger` 继续由调用方明确提供，因为用户输入、系统事件和只读提醒具有不同的副作用边界。`idle_prompt` 必须保持只读，不能由 GM 自行升级为推进世界的回合。

`GameMasterAgent` 负责判断用户是在对话、提问、声明行动、让渡机会还是需要澄清，并选择快速、戏剧或紧迫策略。这三种路径是 Agent 的行为策略和日志标签，不再是能够授予工具权限的确定性 `TurnMode`。

`GameEngine` 和 `ToolExecutor` 仍负责所有硬边界：固定预算、工具参数、对象存在性、信息可见性、行动授权、超时和终止。GM 不能通过自己的语义判断给自己增加权限。

### 单一 Agent Loop

MVP 继续只实现一个真正的 agent loop：`GameMasterAgent`。

三名队友继续由 `generate_character_turn` 生成。角色工具每次只完成一次受约束生成，不能调用其他工具、循环观察结果或直接修改状态。

OODA 只作为 `GameMasterAgent` 选择角色和组织信息的后台启发式，不规定玩家每轮必须依次听取维斯佩拉、萨芙拉和阿兰妮丝的报告。

`GameMasterAgent` 同时负责原 `InputNormalizer` 与 `TurnRouter` 的语义部分：理解用户目的、判断是否需要澄清、选择回合策略以及决定是否调用角色。它只提出工具请求，不负责验证这些请求是否合法。

### 三种回合策略

快速、戏剧和紧迫是 `GameMasterAgent` 的执行策略，不是三个独立工作流组件，也不改变 GameEngine 设定的最高权限和预算。

#### 快速回合

快速回合是普通提问、调查、闲聊和单一行动的默认路径：

```text
用户输入
→ GameMasterAgent 查询必要事实
→ 按需调用零到一名角色
→ 按需请求一次公开检定
→ 提交后果并返回叙事
```

快速回合不整理固定选项，也不为了展示系统而调用所有角色。

#### 戏剧回合

戏剧回合只用于路线、显著代价、最后承重和多人协作：

- 调用一名主要角色表达意见。
- 只有存在真实的不同依据时，才调用第二名角色。
- 主持人可以整理已知风险，但必须允许用户拒绝菜单并提出新方案。
- 用户决定重大风险和授权后，进行一到两次公开检定。
- 选择造成的装备、伤势、位置、关系或危机时钟后果必须持续到后续回合或结局。

普通回合通常调用零到一名角色，任一回合最多调用两名角色。

#### 紧迫回合

当“拉提的注视”达到 5/6 或 6/6 时，主持人进入紧迫表达：只描述正在逼近的危险并询问玩家立即做什么，不默认列出完整菜单。

牺牲、放弃同伴、不可逆资源和关系边界仍需用户确认。MVP 不实现真实倒计时、等待检测或玩家犹豫时的自动状态推进。

### 两种角色生成目的

角色生成区分两种目的，但不建立两个独立系统：

- **独立提议**：用于方案、风险和分歧。第二名角色不读取第一名角色尚未公开的判断，避免盲从和虚假共识。
- **公开接话**：用于吐槽、安慰、反驳和角色互动。后发言角色可以读取前一名角色已经公开的台词，但仍不能读取其私有记忆。

普通回合优先只调用一名角色。第二次生成必须对玩家选择或角色关系提供新的价值。

### 角色行动权限

MVP 使用四类简单权限，不实现通用行为规划器：

| 类别 | 范围 | 规则 |
| --- | --- | --- |
| 自然反应 | 台词、表情、身体语言、合理站位和扶住身边同伴 | 可以直接表现，不改变正式状态 |
| 已授权协作 | 在用户已声明目标内递工具、维持绳索、提醒风险和执行既有分工 | 可以随本次行动一同裁定 |
| 显著代价行动 | 消耗稀缺装备、离队、承担伤势或改变战术 | 必须得到用户明确同意 |
| 用户专属决定 | 路线、牺牲、放弃同伴、重大关系承诺和触碰明确边界 | 只能由用户决定 |

紧急保护是窄例外：每次直接威胁最多允许一名最相关角色反应一次；动作必须符合角色能力，不改变路线，不主动造成自我牺牲，且最多承担一个可见的有限代价。

### 入梦者最小角色卡

用户角色在开场获得三个轻量要素：

- 一句“为什么会反复入梦”的背景钩子，只用于角色提问和结局回声。
- 从观察、灵巧、体力、交涉和意志中选择一个擅长领域。
- 每个主要场景一次“入梦者梦兆”，只能感知某个方向是否深入城市或拉提的注意是否逼近，不能翻译线索、指出机关答案或自动发现隐藏事实。

MVP 不实现完整职业、等级、技能树、装备构筑或角色成长系统。

### 公开骰点

每次检定至少展示技能、目标值、d100 骰值和成功等级，例如：

```text
[灵巧检定] 目标 60｜d100 = 58｜成功
```

骰点和成功等级继续只由 `RuleEngine` 产生，不能被 Agent 修改或重掷。大成功和大失败可以获得一段短叙事和最多一句相关角色反应。

CLI 在行动确认后直接掷骰。3D 骰子、复杂动画和物理骰同步不属于 MVP。

### 最小关系与记忆回流

每名角色只维护：

- 当前关系阶段。
- 少量关系事件标签：尊重、信任、袒露、冲突和修复。
- 一个待回声事件 `pending_echo`。
- 当前阶段允许的称呼、语体和亲密边界。

关系阶段只在场景转换或结局前检查，不在每轮计算。一次事件不能直接完成升级；至少需要用户行动、角色回应，以及一次承担风险、坦白或修复的表现。

`pending_echo` 可以在后续场景被角色自然提起一次，使用后清空。MVP 不实现通用回调调度器，也不保证每条记忆都得到演出。

### 模组内容边界

MVP 对《逃离塔纳里昂》只增加以下轻量内容：

- 商人札记可以记录四名俘虏的“价格与用途”，强化四人共同被工具化的经历，但不增加新线索链或场景。
- 场景二不实现三名角色的专属诱惑支线，继续集中于门印、路标、警告、拾骨者和危机时钟。
- 场景三不让幸存船工突然加入队伍，高潮始终围绕原有四人。
- 当前序失败、装备损失或 5/6 以上时钟确实要求代价时，使用“最后承重”：用户决定牺牲装备，或由自愿角色承担伤势、暴露或拉提印记。
- 状态良好且低时钟完成机关时，不强制触发最后承重。
- 门楼终局作为模组专用协作蒙太奇完成，最多使用两次关键检定，不建立通用多人挑战框架。
- 结局 A/B 回应已经发生的关系与代价；结局 C 在白骨意象后以入梦者从现实惊醒收束。

《逃离塔纳里昂》仍只支持通过阿卡利尔门印和引潮舟离开的正式逃生链。

### 8 周交付边界

CLI 完整试玩是 MVP 的交付门槛。最小 Web UI 只作为时间有余量时的加分项，不作为完成条件。

实现顺序为：

1. 用最小 `TurnContext` 取代 `InputNormalizer`、`FactSet`、`TurnRouter` 和正式 `TurnMode`，并冻结回合策略、权限、入梦者角色卡和模组轻量改动。
2. 完成确定性规则、公开骰点、状态与记忆边界。
3. 实现 `GameMasterAgent` 的快速、戏剧和紧迫策略。
4. 实现角色独立提议、公开接话、关系语体和 `pending_echo`。
5. 接通完整 CLI 回合并验证用户自由行动。
6. 接入三个场景、最后承重、协作蒙太奇和结局。
7. 进行至少三次完整试玩和针对越权、怪招、拒绝菜单的专项测试。
8. 完成可复现 Demo、日志、README 和失败兜底。

## 明确延后

以下内容有价值，但不进入 8 周 MVP：

- 三名角色各自拥有工具循环和跨回合自主任务的完整 Agent。
- 场景二的三种角色专属诱惑支线。
- 幸存船工在门楼求救的道德困境；只有前序充分铺垫并经试玩验证后再考虑。
- 完整角色关系图、通用情感系统和通用回调调度器。
- 实时倒计时、语音打断和玩家犹豫时的自动世界推进。
- 完整入梦者职业、技能树、装备和长期成长。
- 通用多人挑战、战斗和协同动作框架。
- 第二条完整逃生路线、更多塔纳里昂场景和长期探索。
- 跨模组长期记忆、向量检索和角色自主日程。
- 完整 Web UI、立绘动画、骰子动画和语音演出。

## 后果

### 正面后果

- 保留 ADR-001 的单 Agent、状态权威和私密信息隔离。
- 删除重复的输入语义分类层，减少运行时组件、数据契约和测试数量。
- 普通回合减少角色调用、延迟、复述和审批感。
- 玩家不仅负责决定，也拥有自己的能力、骰点和观察入口。
- 角色可以通过低风险行动、接话和事件回声表现为真实同伴。
- 模组新增内容复用现有场景，不扩大逃生路线和地点数量。
- CLI-first 范围更容易在 8 周内完成和测试。

### 负面后果

- 队友自主性仍由单次角色生成模拟，不具备真正长期规划能力。
- GM 可能误判用户意图或选择不理想的回合路径，需要依靠澄清和工具验证恢复。
- 关系系统只能表现少量阶段变化和一次事件回声。
- 场景二在 MVP 中仍以主线解谜和压力为主，人物支线深度有限。
- 门楼协作蒙太奇是模组专用规则，不能直接复用于下一模组。
- Web UI 不再是 MVP 完成门槛，演示体验主要依赖 CLI。

### 风险与缓解

- **GM 把对话误判为行动**：检定请求必须携带行动授权和可追溯的用户原文；ToolExecutor 在授权不足时拒绝调用。
- **GM 选择错误的回合路径**：路径只影响表达和调用选择，不授予额外状态权限；必要时可以直接向用户澄清。
- **统一预算造成普通回合浪费调用**：Prompt 要求快速路径优先，GameEngine 仍设置较小的全局最高预算并记录无价值调用。
- **梦兆变成万能提示**：只允许回答方向和注意程度，并为每个场景编写边界测试。
- **紧急保护越过玩家主导权**：限制为每次威胁一次、有限代价且不得改变路线或主动牺牲。
- **串行接话增加延迟**：普通回合仍只调用一名角色，第二次调用必须有明确价值。
- **最后承重成为强制煽情**：只有既有失败或高时钟需要代价时触发，顺利局不强制发生。
- **关系回声显得机械**：只提供候选事件和语言边界，不要求角色逐字复述历史摘要。

## 考虑过的替代方案

### 方案 A：保留 InputNormalizer、FactSet、TurnRouter 与 TurnMode

未采用。它能在 GM 启动前提供稳定分类，但需要重复理解开放式中文输入；规则实现容易脆弱，LLM 分类又会增加调用和延迟。工具验证已经能够承担真正需要确定性的权限边界。

### 方案 B：每轮执行完整 OODA 与角色汇报

未采用。它结构清晰，但容易公式化，并增加模型调用、复述和玩家审批感。

### 方案 C：三名队友都实现完整 Agent Loop

未采用。短篇模组无法证明长期规划、工具调用和 Agent 间协商能够抵消其工程与延迟成本。

### 方案 D：一次模型调用同时扮演主持人和全部角色

未采用。成本较低，但更容易泄露角色秘密、混淆人格，并让主持人替角色形成虚假共识。

### 方案 E：用户只负责最终决定，不增加角色能力

未采用。用户在 Act 阶段缺少自己的专长，会继续像队伍顾问的审批者。

### 方案 F：把全部评审建议纳入 MVP

未采用。人物诱惑、船工抉择、实时倒计时、通用关系图和完整 Web UI 同时进入范围，会显著提高 8 周交付风险。

## 验收标准

本 ADR 实施后，应满足：

- 运行时不存在独立的 `InputNormalizer`、`FactSet`、`TurnRouter` 或作为权限来源的正式 `TurnMode`。
- `GameMasterAgent` 直接接收包含用户原文和只读状态快照的最小 `TurnContext`。
- GameEngine 在 Agent 启动前确定工具集合、固定预算、超时、只读限制和循环上限。
- GM 对输入的语义判断不能绕过 ToolExecutor、RuleEngine 或 StateCommitter。
- 玩家可以拒绝主持人给出的选项并提出菜单外行动。
- 普通回合通常调用零到一名角色，任一回合最多调用两名角色。
- 玩家至少有一次通过擅长领域或梦兆直接影响局势的机会。
- 所有检定公开显示目标值、骰点和成功等级。
- 至少一次选择产生持续到下一场景或结局的后果。
- 至少一名角色会自然回调此前与玩家共同经历的事件。
- 三名角色的说话方式、欲望和拒绝边界能够被玩家区分。
- 未公开秘密不会泄露，未授权重大行动不会提交，骰点不会被 Agent 修改。
- 角色生成失败、工具非法或循环超限时，本轮仍能保守结束。
- CLI 能在 25—35 分钟内完整跑通三个场景和一个结局。
