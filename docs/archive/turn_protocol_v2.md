# 回合协议设计 v2

> **状态：已归档。** 本文档记录被 [ADR-001](../adr/0001-single-gm-agent-and-character-tools.md) 替代的 multi-agent 设计探索，不再作为实现依据。现行流程见 [回合循环](../turn_loop.md)。

## 文档状态

当前阶段：设计目标草案，已确认多来源回合触发、“主要处理模式 + 事实标记”模型、低耦合原则与“有护栏的混合架构”方向。当前线性总流程暂作为逻辑职责基线，不视为最终执行结构；优先明确 LLM、确定性代码与工具调用之间的职责边界，再对总流程进行改进或重构。

本文档用于定义 Monmusu-agent 多 Agent 回合协议应解决什么问题，以及最终设计应满足哪些条件。当前版本暂不规定具体状态机、发言者评分公式、并发实现、JSON Schema 或类结构；这些内容将在设计目标确认后继续补充。

## 问题背景

现有流程允许 GameEngine 在每轮逐个或并发调用所有 Player Agent，并要求每个 Agent 输出台词与行动。这种方式能够保证所有角色都有内容，但也容易产生以下问题：

- 多名 Player Agent 同时提出完整行动，争夺用户与主持人的注意力。
- 不相关的角色也必须发言，造成线索复述、角色定位模糊和对话冗长。
- Agent 的行动可能互相冲突，却缺少明确的提议、协助、反对和正式执行顺序。
- 每轮调用全部 Agent、检定修正器、Host Agent、一致性检查和记忆更新，会形成较长的串行调用链。
- 为减少延迟而完全并行生成时，Agent 又难以真正回应彼此刚刚说过的话。

回合协议需要在交流质量、用户主导权、角色独立性、规则一致性与响应延迟之间取得平衡。

## 已确认的基础模型

回合协议不再只处理用户输入，而是处理由用户、系统或受控自主机制产生的回合触发。Player Agent 的输出作为候选意图进入同一轮协议，但不能绕过参与计划、权限验证和用户授权直接影响正式游戏状态。

### 多来源回合触发

MVP 支持以下 `RoundTrigger` 来源：

- `user_input`：用户进行对话、询问意见或声明行动。
- `user_yield`：用户明确表示“继续”“你们先说”或暂时把发言与行动机会交给队友。
- `system_event`：GameEngine 根据模组规则创建的场景开始、已安排 NPC 事件或其他确定性触发。
- `idle_prompt`：界面层在用户长时间没有操作时请求一名角色进行提醒或询问。该触发只产生交流，不自动推进游戏时间、危机时钟或世界状态。

字面意义上的“没有任何输入”不构成回合，也不会自动推进游戏。CLI 可以通过显式的 `user_yield` 继续；未来的 Web UI 可以通过继续按钮或定时器产生 `idle_prompt`。

MVP 阶段 Host Agent 不作为独立 `RoundTrigger` 来源。Player Agent 的主动建议也必须由 `user_yield`、`idle_prompt`、已有分工或系统允许的紧急反应触发，不能自行递归开启无限对话。

### 总流程

```text
RoundTrigger
  → TriggerNormalizer：把不同来源转成统一事实标记
  → FactSet：记录来源、目标、意图和承诺程度
  → TurnRouter：确定性推导主要处理模式
  → ParticipationPlanner：生成 ParticipationPlan
  → Selected PlayerAgents：生成 CandidateIntents
  → AuthorityValidator：检查来源权限与用户授权
  → ResolutionPlanner：生成 ResolutionPlan
  → RuleEngine / HostAgent：检定并产生 Resolution
  → StateCommitter：验证并提交 GameState、Memory 与 EventLog
```

该流程中的名称表示逻辑职责，不要求每一项都实现为独立进程、服务或类。MVP 可以在一个模块化单体应用中实现，只要阶段边界和数据契约保持清晰。

当前图示偏向线性 workflow，只回答“一轮中存在哪些逻辑职责及其因果顺序”，尚未表达确定性快速路径、受限 Agent Loop、按需工具调用、循环终止与降级分支。它是后续讨论职责边界时使用的基线，不是已经确定的最终运行流程。待职责、权限、数据契约和调度策略明确后，应重新设计总流程，并允许重排、合并或拆分现有阶段。

### 阶段职责

#### RoundTrigger

- 只表示“为什么现在需要运行一次协议”。
- 携带来源 ID、原始输入或结构化系统事件，以及稳定的 `round_id`。
- 不直接决定调用哪些 Agent，也不修改游戏状态。

#### TriggerNormalizer 与 FactSet

- 用户自然语言通过输入解析器提取事实标记。
- `user_yield`、`system_event` 和 `idle_prompt` 已经是结构化输入，只需通过对应适配器转换为同一 `FactSet`。
- Player Agent 与 Host Agent 的结构化输出不重新使用用户自然语言解析器，而由各自适配器转换为候选意图或裁定结果。
- `FactSet` 描述触发中存在什么，不包含发言者选择、并发策略或组件调用决定。

#### TurnRouter

- 根据 `FactSet` 与只读游戏状态推导唯一的主要处理模式。
- 只负责选择主流程，不负责选择具体发言者、调用模型或执行检定。
- 下游组件直接使用路由结果，不再各自重复解释标记优先级。

#### ParticipationPlanner 与 ParticipationPlan

- 根据主要模式、点名对象、角色定位、紧急程度和曝光记录选择本轮需要调用的 Player Agent。
- 为被选 Agent 指定主要发言、协助、反对、反应或自主提议等参与角色。
- 只决定“允许谁以什么身份生成候选内容”，不提前承诺其行动一定会执行。
- 未被选择的 Agent 不产生模型调用，也不需要返回“保持沉默”。

#### CandidateIntents

- 被选中的 Player Agent 输出台词、建议、协助意图或自己的行动提议。
- 候选意图不是正式事件，不能直接进入 GameState，也不能被 Host Agent 当作已经发生的行动。
- Agent 可以建议用户采取某项行动，但不能提交、改写或命令用户行动。
- Agent 可以提出自己的行动；普通行动需要用户明确同意、已有分工授权或协议认可的紧急反应权限才能正式提交。

#### AuthorityValidator

- 根据意图来源、目标、行动所有者和授权状态判断候选意图是否可以进入下一阶段。
- 拒绝 Player Agent 替用户行动、替其他 Agent 行动、创造世界事实或绕过用户选择的内容。
- 可以把合法建议保留为用户可见台词，同时阻止其作为正式行动进入裁定。
- 权限验证使用确定性规则，不依赖 Host Agent 临时决定谁拥有什么权限。

#### ResolutionPlanner 与 ResolutionPlan

- 把用户已经提交的行动、获得授权的 Agent 行动、合法协助和需要裁定的系统事件整理为正式事件集合。
- 区分仅展示的台词、等待用户选择的互斥提议和本轮真正提交的行动。
- 两项行动互相排斥时，不得同时提交；应保留为选项或按照用户已经明确的优先级处理。
- `ResolutionPlan` 是 RuleEngine 与 Host Agent 唯一应当接收的本轮行动来源。

#### RuleEngine、Host Agent 与 Resolution

- RuleEngine 判断行动合法性、是否需要检定，并产生确定性的掷骰与规则结果。
- Host Agent 根据 `ResolutionPlan`、规则结果和模组边界生成叙事与受限状态更新建议。
- Host Agent 不读取未通过权限验证的候选行动，也不能把普通建议叙述为已经执行。
- `Resolution` 仍然只是待提交结果，不能由 Host Agent 直接写入正式状态。

#### StateCommitter

- 是正式 `GameState`、公共记忆、私有记忆和事件日志的唯一写入入口。
- 验证 Host Agent 建议是否符合 schema、模组边界、规则结果与信息公开权限。
- 拒绝非法更新时保留原状态，并记录可观察的拒绝原因。
- 其他组件只接收只读状态快照，不直接共享或修改可变游戏状态。

### 事实标记

事实标记用于描述一次 `RoundTrigger` 中实际出现了什么，不直接决定系统应调用哪些组件。它们应尽量保持客观、细粒度，并允许一次触发同时包含多种意图。

初步需要表达的事实包括：

- 触发来源是用户、系统还是空闲提醒。
- 用户点名了哪些角色。
- 用户是在询问意见、进行日常对话，还是声明行动。
- 输入中是否包含可能改变世界状态的行动。
- 行动是建议、假设、有条件行动，还是已经明确提交的行动。
- 用户是否要求多名队友分别发表看法。
- 当前表达是否带有紧急、立即执行或打断性质。
- 系统事件是否要求世界裁定，还是只要求展示场景信息。

事实标记回答的是“触发中包含了什么”。例如：

```text
source_type = user_input
direct_targets = [vespera]
asks_opinion = true
has_world_action = true
action_commitment = committed
requests_multiple_views = false
urgency = normal
```

事实标记不应直接包含以下系统决策：

- 是否调用 Host Agent。
- 最多允许几名 Player Agent 发言。
- 选择谁担任主要发言者。
- 本轮使用并行还是串行生成。
- 行动是否需要检定。

这些内容应由 TurnRouter、ParticipationPlanner、ResolutionPlanner 或 RuleEngine 根据事实和当前游戏状态决定。

### 主要处理模式

主要处理模式用于选择本轮应走的主流程。它不是对用户原话的完整描述，而是 TurnRouter 对事实标记进行优先级判断后得到的路由结果。

初步考虑的主要模式包括：

- `direct_dialogue`：定向交流或不需要世界裁定的日常对话。
- `group_discussion`：用户主动征求多个方案或队伍意见。
- `action_resolution`：存在已经提交、可能改变世界状态的行动。
- `urgent_reaction`：需要立即处理的危险、打断或紧急行动。

主要处理模式回答的是“系统接下来走哪套流程”。例如：

- `direct_dialogue` 通常只调用被点名的 Agent，不调用 RuleEngine 与 Host Agent。
- `group_discussion` 选择少量能够提供不同价值的 Agent，不提交世界行动。
- `action_resolution` 将确认提交的行动交给 RuleEngine，并在需要时调用 Host Agent 裁定。
- `urgent_reaction` 缩短或跳过普通讨论，优先处理安全相关行动。

### 二者的关系

主要处理模式由事实标记推导，但不会取代事实标记。主要模式负责确定主流程，事实标记继续负责提供主流程中的具体细节。

例如，用户输入：

> “维斯佩拉，你去门外看看有没有人，其他人先别动。”

可以提取为：

```text
direct_targets = [vespera]
has_world_action = true
action_commitment = committed
requests_multiple_views = false
urgency = normal
```

TurnRouter 据此推导：

```text
turn_mode = action_resolution
```

随后：

- `action_resolution` 决定本轮进入行动与裁定流程。
- `direct_targets` 决定维斯佩拉是最相关的队友。
- `requests_multiple_views = false` 阻止另外两名 Agent 无必要地发表意见。
- `urgency = normal` 表示不需要使用紧急打断流程。

### 单一事实来源

- 各来源适配器只负责产生统一事实标记，不应独立输出主要处理模式。
- TurnRouter 使用确定性规则从事实标记与当前游戏状态推导主要模式。
- 主要处理模式和事实标记可以同时写入本轮协议记录，但主要模式必须标记为派生字段。
- 下游组件不应自行重新判断主要模式，也不应各自维护一套不同的标记优先级。
- 如果事实标记无法形成合法模式，TurnRouter 应进入保守澄清或降级流程，而不是让不同组件自行猜测。

### Player Agent 的权限边界

| 行为 | MVP 权限 |
| --- | --- |
| 提出用户可以考虑的方案 | 允许 |
| 命令、改写或提交用户行动 | 禁止 |
| 提出自己的行动 | 允许 |
| 未经授权提交普通自主行动 | 禁止 |
| 执行用户明确同意或既有分工中的行动 | 允许进入权限验证 |
| 进行协议明确允许的紧急保护反应 | 允许进入权限验证 |
| 替其他 Agent 决定行动 | 禁止 |
| 宣布行动结果、NPC 反应或世界事实 | 禁止 |

这种边界使 Player Agent 仍然是能够行动的队友，而不是只会提供建议的旁白，同时保证她们不能控制用户或绕过正式裁定。

## 核心设计目标

### 1. 保持用户的主角与决策者地位

- 用户决定主要路线、是否冒险、采用哪项建议以及如何分配队伍任务。
- Player Agent 可以提出建议、风险和分歧，但不能用多人共识替用户作出决定。
- 当用户已经明确行动时，队友应优先协助、提醒或回应，而不是擅自开启三个新的行动方向。
- 协议应保证每个需要用户选择的回合都有清晰、数量可控的选项。

### 2. 让沉默与协助成为合法参与方式

- Player Agent 不需要每轮都发表台词或执行独立行动。
- 没有独特信息或相关能力的角色可以保持沉默、表示简短支持或协助另一名角色。
- 协议不应为了平均分配台词而制造无意义发言。
- “本轮未发言”不等于角色离开场景、失去关注或没有参与队伍行动。

### 3. 每轮只突出少量真正相关的角色

- 普通回合应有一名主要发言者或行动者，必要时再加入一名协助者或持不同意见者。
- 用户点名某名角色时，该角色拥有最高回应优先级；其他角色只在紧急危险或重要冲突下介入。
- 发言权应优先考虑当前问题与角色定位的相关性，而不是固定轮流。
- 协议也应记录角色曝光情况，避免同一角色长期垄断所有重要回合。

### 4. 让多 Agent 交流产生互补，而不是复述

- 第二名发言者必须提供新的证据、风险、可行性判断、情感反应或不同方案。
- 多名 Agent 不应使用不同措辞重复同一条公开线索。
- 角色分歧应围绕实际选择与代价展开，而不是为了展示性格进行无休止争吵。
- 协议应利用角色卡中的团队定位，使侦察、解释、执行和情感反应在合适的回合得到不同程度的关注。

### 5. 区分提议、协助、反应与正式行动

- 角色说出一个方案，不应自动等同于该方案已经进入裁定。
- 协议需要能够表达角色是在提出建议、回应他人、协助行动、反对方案，还是正式尝试执行行动。
- 同一时刻存在互相排斥的行动时，应先交还用户选择，不能把所有行动同时送去裁定。
- Host Agent 只裁定被协议确认提交的行动，不把闲聊、假设或情绪表达误认为已经发生的事件。

### 6. 保证回合顺序清晰且因果一致

- 用户输入、队友反应、行动提交、规则检定、主持人裁定和状态更新必须具有明确顺序。
- Agent 不能回应自己尚未看到的台词，也不能引用尚未公开的裁定结果。
- 并行生成的内容必须能够在不假装互相听见的前提下组合。
- 需要真实对话承接的回合可以允许更深的串行生成，但这应当是有意识的例外。

### 7. 在不明显牺牲交流质量的前提下降低延迟

- 普通回合不应默认调用全部 Player Agent。
- 没有被选中发言或行动的 Agent 不应为了返回“保持沉默”而产生一次模型调用。
- 可以并行且互不依赖的生成应尽量并行；需要阅读前一名角色台词的回应才使用串行调用。
- 一致性检查、语境修正和记忆摘要等辅助调用应按需要触发，而不是无条件阻塞每轮输出。
- 协议应允许先展示安全的队友提议，再等待主持人裁定世界结果，以改善用户感受到的响应速度。

### 8. 保持角色人格、私有记忆与信息边界

- 发言调度不能把三名 Player Agent 合并成一个共享人格。
- 每名 Agent 只能读取自己有权知道的公开信息与私有记忆。
- 发言者选择过程不能泄露隐藏动机，也不能让其他 Agent 自动知道某人为何被选中。
- 未发言角色的私有状态仍可随公开事件更新，但不能凭空获得其他角色尚未披露的秘密。

### 9. 保持 Host Agent 与规则系统的裁定权

- Player Agent 只能提出或尝试行动，不能宣布成功、失败、NPC 反应、线索发现或世界状态变化。
- Host Agent 负责叙事裁定，但不能修改代码已经确定的掷骰结果或替用户与 Player Agent 决定行动。
- GameEngine 与 RuleEngine 负责回合阶段、合法行动、检定和确定性状态更新。
- 回合协议必须明确每项数据由谁产生、由谁验证、何时成为正式事件。
- MVP 阶段的 Host Agent 不独立发起新回合，也不在缺少 `ResolutionPlan` 的情况下自行推进场景、危机时钟和 NPC 行动。
- Host Agent 可以在 schema 允许范围内提出叙事与状态更新建议，但必须由 GameEngine 根据模组边界和规则验证后才能生效。

### 10. 支持失败降级，不让单个 Agent 阻塞整轮

- 某个 Player Agent 超时、输出非法或暂时不可用时，其他角色和主持人仍应能够继续回合。
- 协议应允许取消非必要的协助发言，并把主行动安全地送入裁定。
- 降级行为不能擅自替失败的 Agent 编造重要决定、秘密坦白或关系变化。
- 重试次数、超时与保守模板应有明确上限，避免为了修复一条队友台词无限增加延迟。

### 11. 让调度过程可观察、可测试

- 系统应记录本轮为何选择某名 Agent，以及其他 Agent 为何保持沉默。
- 发言者选择、行动提交和 Host 裁定应拥有稳定的回合 ID 与事件顺序。
- 测试应能够在不调用 LLM 的情况下验证点名优先、相关性选择、发言人数限制、行动冲突和超时降级。
- 日志需要区分用户可见台词、正式行动、内部调度原因和私有动机，避免调试信息泄露到游戏界面。

### 12. 为后续扩展保留空间

- MVP 以 1 名用户、3 名 Player Agent 和 1 名 Host Agent 为主要目标，但协议不应把角色姓名或《逃离塔纳里昂》的场景写死在核心代码中。
- 后续可以增加或减少 Player Agent，而不必重写整个回合状态机。
- 协议应允许未来加入主动插话、队友间短对话、特殊状态打断和不同延迟模式，但 MVP 不需要一次实现全部扩展。

### 13. 保持组件职责单一与低耦合

- 每个组件只负责一个主要阶段，不同时承担自然语言解析、发言选择、权限判断、规则裁定和状态写入。
- 组件之间通过带版本的结构化数据契约交接，不依赖彼此的内部类、提示词文本或可变对象。
- Player Agent、Host Agent 和调度组件不能直接互相调用；调用顺序由 GameEngine 或专门的回合协调器统一编排。
- 所有组件读取同一回合的只读状态快照，正式状态只允许通过 StateCommitter 更新。
- TurnRouter、ParticipationPlanner 和延迟策略应可以独立替换，而不要求修改角色实现、Host Agent 提示词或规则引擎。
- RuleEngine 不解析角色台词来决定规则事实；LLM 组件也不直接执行掷骰、修改时钟或写入状态。
- 低耦合以便于测试和替换为目标，不要求 MVP 使用微服务、消息队列、依赖注入框架或复杂事件总线。

### 14. 采用有护栏的混合架构

- 回合协议定义不可绕过的权限、状态、信息与因果边界；Agent Loop 只负责在这些边界内选择下一项合法工作。
- LLM 适合处理自然语言理解、语义判断、内容生成、角色表达和需要上下文权衡的软决策；普通代码适合处理权限校验、规则计算、状态写入、调用预算和其他必须稳定复现的硬约束。
- Agent Loop 不能直接调用任意组件。协调器在每个协议阶段只能看到当前允许使用的工具，工具自身还必须再次验证输入与调用前置条件。
- Player Agent 与 Host Agent 的输出默认是候选内容或状态更新建议，不能仅因一次工具调用成功就自动成为正式事件。
- MVP 原则上只设置一个由 GameEngine 管理的回合协调循环。Player Agent 与 Host Agent 作为受调度的结构化生成节点，不各自启动能够递归调用其他 Agent 的独立循环。
- 简单、明确且高频的回合应保留确定性快速路径；只有需要语义权衡、补充生成或动态决定下一步时才进入有限的 Agent Loop。
- Agent Loop 必须具有最大迭代次数、模型调用预算、允许工具集合、超时与强制结束条件，不能以“继续思考”为由无限延长回合。
- 架构应允许将某项职责在 LLM、轻量模型、评分策略与确定性规则之间替换，而不改变权限边界和正式状态提交规则。
- 采用 Agent Loop 是回合协调的实现策略，不取代 `RoundTrigger`、候选意图、权限验证、裁定计划和状态提交等协议概念。

## 优先级

### P0：必须满足

- 用户保留最终选择权。
- 普通回合不再要求所有 Player Agent 发言。
- 系统能够区分提议、协助、反应和正式行动。
- 未提交的建议不会被 Host Agent 当作已发生行动。
- 角色私有记忆与隐藏动机不会互相泄露。
- 单个 Agent 失败不会阻塞整轮。
- 正常行动回合的模型依赖深度显著低于现有全量调用流程。
- TurnRouter 是主要处理模式的唯一推导入口，下游组件不重复分类。
- Player Agent、Host Agent 和规则组件不能直接修改正式状态。
- 正式状态更新只通过 StateCommitter 提交，并保留验证结果。
- Agent Loop 只能调用当前协议阶段允许的工具，并受到迭代次数、调用预算和终止条件限制。
- LLM 产生的候选内容不能绕过确定性权限与状态校验直接生效。

### P1：应当满足

- 发言选择兼顾相关性与跨场景曝光平衡。
- 两名 Agent 发言时能够提供互补内容或真实分歧。
- 直接点名、紧急危险和明确队伍讨论具有不同调度方式。
- 调度决策、事件顺序和降级过程可以通过日志复盘。
- 发言选择、权限策略和并发策略能够通过稳定接口独立替换。

### P2：可以延后

- 三名以上 Agent 的复杂自由讨论。
- 根据实时延迟自动切换模型或生成策略。
- 允许 Agent 主动打断其他角色的流式发言。
- 面向不同模组自动学习最优发言策略。
- 引入具有 Keeper 主动性的 Host Agent，使其能够在受控预算内主动制造压力、调整节奏、重现遗漏线索或发起模组允许的 NPC 与环境事件。

## 非目标

- 本协议不负责设计具体角色人格、模组剧情、线索内容或检定数值。
- 本协议不追求模拟完全自由、无限轮次的真实多人聊天。
- 本协议不保证每名 Agent 在每个场景拥有完全相同的台词数量。
- 本协议不通过一个模型调用同时扮演所有角色来换取最低延迟；是否提供这种快速模式可在后续单独讨论。
- 本协议不允许为了制造队友互动而削弱用户的决定权或延长无意义争论。
- MVP 不实现 Host Agent 自主决定“何时该发生新事件”的 Keeper 主动性；该能力需要单独设计触发条件、节奏预算、状态权限和可回滚边界。
- 低耦合不等于把 MVP 拆成分布式系统；本协议不要求微服务、消息队列或通用工作流引擎。

## 初步验收标准

- 用户直接点名一名 Agent 时，普通情况下只有该 Agent 生成完整回应。
- 普通回合最多有一名主要发言者和一名提供不同价值的辅助发言者。
- 未被选择的 Agent 不产生模型调用，也不会输出占位台词。
- 当两项行动互相排斥时，系统不会同时提交，而是要求用户选择或明确优先级。
- 纯角色对话或询问不需要世界裁定时，可以跳过 Host Agent 调用。
- 正常行动回合原则上只包含“被选 Player Agent 生成”和“Host Agent 裁定”两层串行模型依赖；额外调用必须有明确触发原因。
- 任一 Agent 超时或输出非法时，系统能够在有限重试后继续回合，并保留合法的用户行动。
- 日志能够说明发言者选择、行动提交、裁定和状态更新的先后关系，同时不向用户泄露私有调度信息。
- 更换 ParticipationPlanner 的选择策略时，不需要修改 Player Agent、Host Agent 或 RuleEngine 的实现。
- 除 StateCommitter 外，任何组件尝试写入正式状态都应在测试中失败。
- 每个阶段可以使用固定输入样例独立测试，不需要启动完整 LLM 调用链。
- `user_yield` 能触发一次受限的队友主动提议；`idle_prompt` 只能产生交流，不能推进危机时钟或场景状态。
- 简单回合可以通过确定性快速路径完成，不必为了统一形式启动完整 Agent Loop。
- 即使协调 LLM 请求了越权工具、非法参数或超出预算的调用，系统也能拒绝调用并安全结束或降级本轮。

## 后续待讨论

以下问题按依赖关系讨论。当前先完成职责、护栏、数据契约与调度策略，再改进或重构偏线性的总流程，避免让现有 workflow 形式反向限制混合架构。

### 第一组：LLM、代码与工具的职责边界

- 哪些判断必须由确定性代码完成，哪些判断可以交给 LLM，哪些适合采用“LLM 提议、代码验证”。
- 回合协调 Agent 可以看到和调用哪些工具；不同协议阶段如何限制工具可见性与调用顺序。
- 哪些简单回合走确定性快速路径，哪些情况才启动 Agent Loop。
- Agent Loop 的终止条件、最大迭代次数、模型调用预算、超时与降级责任分别由谁执行。
- Host Agent、检定语境修正、一致性检查和记忆更新分别在什么条件下调用，以及它们属于循环步骤还是循环结束后的固定步骤。

### 第二组：权限与正式状态边界

- 普通 Agent 行动、既有分工授权与紧急反应权限如何表示和撤销。
- 工具调用的前置条件由谁验证，协调 LLM 请求越权工具时系统如何拒绝并恢复。
- `CandidateIntent`、工具调用结果、`Resolution` 和正式事件之间如何转换，哪些结果必须再次确认。
- 结构化数据契约如何分层，哪些字段属于公开信息、私有信息与仅供调试的内部信息。

### 第三组：最小数据契约

- `RoundTrigger`、`FactSet`、`ParticipationPlan`、`CandidateIntent`、`ResolutionPlan` 和 `Resolution` 的最小字段与版本规则。
- Agent Loop 是否需要单独的 `RoundContext`、循环步骤记录、工具调用记录和结束原因。
- 主要发言者、协助者和反对者分别使用什么输出结构。

### 第四组：调度、对话与延迟策略

- 发言者选择由确定性规则、评分系统、轻量模型还是协调 Agent 完成。
- 哪些回合允许并行生成，哪些回合需要真正的串行对话。
- 发言曝光平衡应按回合、场景还是整局游戏统计。
- 超时、重试、降级模板和模型调用预算的具体数值。

### 第五组：改进或重构主要流程

- 将当前线性职责链重构为“确定性入口与护栏 + 可选快速路径 + 受限 Agent Loop + 确定性提交”的混合执行结构。
- 明确哪些职责始终按固定顺序执行，哪些职责由协调 Agent 按需调用，哪些可以完全跳过。
- 定义 Agent Loop 的入口、可用工具变化、循环状态、退出条件，以及退出后必须经过的验证与提交阶段。
- 判断现有阶段应保留、合并、拆分还是改为工具，并重新绘制能够表达分支与循环的总流程图。
- 设计快速路径与 Agent Loop 之间的选择、回退和降级关系，保证两条路径遵守同一权限与状态协议。

### 第六组：完善主要处理模式

- 在新总流程明确后，重新判断四种初步主要处理模式是否足够。
- 事实标记的最小字段集合，以及哪些字段由代码提取、哪些允许 LLM 辅助提取。
- TurnRouter 是否保持完全确定性，以及它与协调 Agent、快速路径和 Agent Loop 的关系。
- TurnRouter 从事实标记推导主要模式时采用什么优先级与冲突处理规则。

### 第七组：后续扩展

- 后续 Keeper 主动性应允许 Host Agent 影响哪些状态，以及如何限制主动事件的频率、强度和剧情范围。
